# Excel Combiner v1.7 产品需求文档

> 文档状态：已冻结 v1.0，发布候选已完成本地验证
> 基线版本：1.66  
> 目标版本：1.7  
> 建议主题：可信内核与自动化入口  
> 创建日期：2026-10-04  
> 产品负责人：OrangeMoon  

## 1. 版本结论

v1.7 建议做一次“用户行为基本不变、内部可信度明显提升”的工程型版本。它不以新增大量按钮为目标，而是把合并、拆分的业务处理从 tkinter 界面和全局状态中分离出来，建立可由 GUI、CLI 和自动化测试共同调用的核心层。

这一版完成后，普通用户仍可沿用现有图形界面；开发和验收人员可以通过 CLI 重复执行同一任务、检查退出码和结果文件。它将成为 v1.8 配置界面、v1.9 预览编辑、后续反向填表继续开发的稳定基线。

## 2. 用户与损失

### 2.1 目标用户

- 使用图形界面进行 Excel 合并或拆分的办公人员；
- 需要重复执行、批量验证或排查问题的产品负责人和维护人员；
- 后续需要在现有能力上增加配置、预览和反向填表的开发者。

### 2.2 当前问题

合并和拆分的核心逻辑仍与 tkinter 弹窗、全局变量和单文件流程紧密耦合。新增功能或修复问题时，容易出现以下损失：

- 必须通过人工点击才能验证部分流程，回归成本高；
- 业务逻辑与界面改动互相影响，修复一个问题可能带来新的行为漂移；
- 无法通过稳定命令重复执行相同任务，难以形成真正的 CLI 黑盒测试；
- PyInstaller 打包是否可启动没有成为发布门槛；
- 后续配置面板、预览编辑和反向填表缺少可复用的核心接口。

## 3. 产品目标

### G1 保持现有用户流程

现有合并和拆分图形界面的主要操作顺序、数据规则和输出语义保持一致。除修复被测试证明的问题外，不主动改变业务行为。

### G2 建立无界面核心层

读取、匹配、分组、公式处理、写入和异常汇总可以在不启动 tkinter、不依赖显示器的情况下调用。核心函数通过明确参数接收输入，并通过明确返回值报告结果。

### G3 提供可自动执行的 CLI

提供合并和拆分两个命令入口。CLI 可以接收明确的文件路径、输出路径和必要配置，不弹出交互窗口，并通过退出码区分成功、输入错误和处理失败。

### G4 建立发布门槛

在现有文件级回归基础上，增加 CLI 黑盒测试、Windows 打包验证和最小 EXE 启动冒烟。发布前必须完成版本同步、公开测试、CI 和隐私检查。

### 4.1 核心层与界面分离

| ID | 需求 | 优先级 |

| R3 | 核心层不得直接弹窗；需要用户决定的情况返回结构化问题或错误，由 GUI/CLI 分别处理 | P0 |

### 4.2 CLI 自动化入口

| ID | 需求 | 优先级 |
| --- | --- | --- |
| C1 | 提供 `merge` 命令，显式指定模板、输入文件、输出路径和 Sheet 映射配置 | P0 |

CLI 在 v1.7 中定位为受支持的高级入口和自动化测试入口，不替代普通用户的图形界面。

## 5. 行为契约

### 5.1 GUI

- 用户仍可直接运行合并或拆分 Python 入口；
- 现有文件选择、配置、确认和完成提示继续存在；
- 相同输入和相同选择应得到与 1.66 等价的输出数据、文件命名和异常记录；
- GUI 取消操作不得留下半成品输出。

### 5.2 CLI

- 所有路径和业务选择必须显式提供；
- CLI 不得等待弹窗、隐藏输入或人工点击；
- 成功时必须能定位输出文件；
- 失败时不得把部分输出伪装成成功结果；
- 错误信息必须说明是参数问题、输入兼容问题还是处理失败。

### 5.3 文件输出

- 合并端继续遵守 1.66 的公式转值规则；
- 拆分端继续遵守 1.66 的公式移动规则和已公开边界；
- `.xlsx/.xlsm` 普通数据单元格保留原有数值、布尔、日期和文本类型；表头统一按文本进行列名匹配；
- CSV 没有可靠的 Excel 类型元数据，继续按文本读取；
- 输出文件必须通过 ZIP/OpenXML 完整性检查并可被 openpyxl 重新打开；
- 公开最小样例的输出必须能被 Microsoft Excel 正常打开、计算、保存并再次打开，且没有修复提示或修复日志；
- 不支持保留的样式、宏或复杂对象必须在处理前向用户说明，不能静默丢失。

## 6. 验收标准

满足以下全部条件，v1.7 才可以请求发布确认：

1. v1.66 的 35 项回归测试全部通过；
2. 新增的 CLI 黑盒测试全部通过，且真实启动独立进程；
3. 核心处理模块在无图形显示环境中可以导入并运行；
4. 核心处理模块不导入 tkinter，不依赖一次任务之外的可变全局状态；
5. 使用公开合成样例比较 1.66 与 1.7，关键输出数据和异常语义一致；
6. Windows 和 Ubuntu 的 CI 全绿；
7. Windows PyInstaller 构建成功，构建产物完成最小启动冒烟；
8. 公开 Excel 样例正常打开，无文件修复模式；
9. 两个 Python 入口与 README、PRD、CHANGELOG 的版本号均为 1.7；
10. Git 暂存清单和公开 PR 说明不含内部测试材料或来源信息；
11. README 已写明本版没有覆盖的兼容边界；
12. 产品负责人审阅验证证据并明确确认发布。
13. 合并与拆分的公开合成样例均通过数据类型保真测试，拆分公式由 Microsoft Excel 重算后得到预期数值。
14. 合并与拆分的行数/分组守恒、失败原子性和原文件不变均有可重复证据。
15. 样式、公式、宏/VBA、图表、图片、形状和复杂对象矩阵均形成“通过/明确不支持/待修复”结论；存在静默丢失风险时不得发布。
16. 合并、拆分打包 EXE 各完成至少一次真实处理流程，而不只运行 `--version`。

## 7. 本版本明确不做

- 不开发反向填表、交集裁剪、全量替换或仅追加；
- 不做配置面板、配置保存加载和复杂界面美化；
- 不做拆分结果预览、手动调整分组、增删查改；
- 不建立完整 Operation 插件体系，不落地完整 Workbook 中间模型；
- 不开发 Web、任务队列、数据库或云端服务；
- 不接入任何 LLM、自然语言操作或 AI 自动修改 Excel；
- 不承诺完全保留所有图表、图片、形状、ActiveX、签名和外部连接；
- 不因为重构而改变已发布的列匹配、公式、命名和异常处理语义；
- 不把内部测试材料及其衍生输出、截图、字段或验证说明上传到 GitHub。

## 8. 实施顺序

### M0 冻结需求

确认本 PRD 的版本定位、CLI 定位、EXE 形式和发布门槛。未冻结前不修改生产代码。

### M1 固定 1.66 基线

整理公开合成样例和关键输出快照，确认现有 35 项测试与 1.66 标签一致，补足重构前缺失的行为契约测试。

### M2 提取核心层

先提取读取、写入和结果模型，再迁移合并、拆分流程。每次迁移保持现有测试持续通过，不进行一次性大改。

### M3 建立 CLI

在核心层稳定后增加 merge、split、`--help` 和 `--version`，再增加 subprocess 黑盒测试。

### M4 GUI 接回核心层

让现有 GUI 仅负责收集选择和展示结果，使用与 CLI 相同的核心服务。

### M5 打包与兼容验证

完成 Windows PyInstaller 构建、最小 EXE 启动、公开工作簿兼容检查和 README 边界更新。

### M6 发布候选

同步 1.7 版本号和发布文档，建立草稿 PR，CI 全绿后提交验证报告，由产品负责人确认是否合入 main 并创建 1.7 标签。

## 9. 风险与回退

| 风险 | 控制措施 |
| --- | --- |
| 模块化过程中出现行为漂移 | 先补行为测试，分步迁移，每一步保持测试通过 |
| CLI 与 GUI 形成两套逻辑 | 两者必须调用同一个核心服务，禁止复制业务逻辑 |
| 为追求架构完整而扩大范围 | 以本 PRD 的“不做事项”为边界，Operation 和中间模型留到后续版本 |
| PyInstaller 在不同 Python 版本表现不同 | 在 Windows CI 固定构建环境，并对产物执行最小启动冒烟 |
| 输出兼容性回退 | 使用公开最小样例进行重新打开和 Excel 冒烟，异常则停止发布 |
| 发布后发现严重回归 | 保留 1.66 标签；通过新的修复提交恢复行为，不改写 main 历史 |

## 10. 已冻结的产品决策

产品负责人已于 2026-10-04 确认以下方案：

1. v1.7 定位为可信内核改造，普通 GUI 行为基本不变，不加入反向填表或界面大改；
2. CLI 作为正式受支持的高级入口，而不只是临时测试脚本；
3. v1.7 继续保留合并、拆分两个普通用户入口，不在这一版合成一个全新主界面；
4. Windows EXE 构建成功和最小启动冒烟列为发布硬门槛；完整 GUI 自动化仍不作为 v1.7 硬门槛。
5. 产品负责人于 2026-10-05 增补发布测试规则：数据类型不得改变，输出不得触发 Excel 修复，并必须检查样式、公式、宏及复杂对象的保留或用户提示。
